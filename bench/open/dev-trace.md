## 4. 问题

### 问题 A：把普通功能判成了 framework-level

trace 里 agent 在 17:04:22 明确写：

> Route: **framework-level feature** ... do one structural review before coding

于是它写了 `design.md`，并在写代码前派结构审。最后代码只有 `records.py` 一个文件、约 144 行改动；这是普通功能，不是新架构。这个判断直接触发了：

- 写代码前结构审：277.7 s
- 结构审复查：53.6 s

**可避免时间：约 331 s（5.5 分钟）。**

### 问题 B：reviewer 选择失败，回退到了错误的 agent

`~/.pi/agent/agents/reviewer.md` 里写的是：

```yaml
model: claude-sonnet-4-5
```

这个模型名在多个 provider 之间有歧义，第一次调用 1.2 s 就失败。随后 agent 回退到 `astra`：

```yaml
# ~/.pi/agent/agents/astra.md
description: Implementation worker for dunhuang-viewer
model: openai/gpt-6-astra
```

`astra` 是另一个项目的实现 worker，不是 reviewer，而且模型更重。后 4 次审核全部用它，合计 803 s。  
**问题不在“审核本身慢”，而在“审核用了错误的人/模型”。**

### 问题 C：全量审 + 修复后全量复查

代码审本身 302.9 s；修 3 条必须改后，又用 168.7 s 做整轮复查。复查里 3 条都是局部修复（同文件保护、bool 校验、文档去重），完全可以只审修复 diff 或做快速验证。

**可避免时间：最多 169 s（2.8 分钟）；至少可缩到 30–60 s。**

### 问题 D：重复跑全套检查

40 次 bash 里，有 21 次包含 pytest / doc_guard / spec_check，合计 120.3 s。多个切片结束都跑了全量，修复后又跑了多次。

**可避免时间：约 50–90 s。**

### 问题 E：68 个 assistant turn

主模型 68 轮、408.5 s。每轮平均约 6 s，很多轮只做一个小编辑或一次检查。不是最大头，但可以通过批量编辑、减少重复检查来压。

## 5. 优化后的目标

粗略估算：

| 改动 | 预计节省 |
|---|---:|
| 普通功能不写 `design.md` / 不做写前结构审 | ~331 s |
| reviewer 改用明确可用的快模型（或同模型独立上下文） | 取决于模型；至少去掉错误 agent 的重模型 |
| 修复后只审 diff，不做全量复查 | ~110–169 s |
| 合并全量检查（2–3 次而不是 21 次） | ~50–90 s |
| **合计** | **约 8–10 分钟** |

所以 22.4 分钟压到 **9–12 分钟**是现实的；如果审核模型本身也换快，目标可以更低。前提是保留最终一次真实审核和测试，不靠“不审”换时间。

## 6. 建议的规则改动

1. **路由**：只有新增模块、改全局结构/契约、跨仓库迁移才算 framework-level；单文件 CLI 的新命令一律普通功能。
2. **普通功能审核一次**：在所有切片完成后做一次全量代码审；不要写前结构审。框架级才保留“写前结构审”。
3. **reviewer 固定配置**：用具体 provider/model，或继承主模型；禁止回退到任意用户 agent。`reviewer` 失败时应报错并让主会话选择同模型独立上下文。
4. **审核输入收窄**：只给当前 spec、变更 diff、基线；不要附全套 docs/测试。审核默认不跑全量测试，父会话已经跑过。
5. **复查只审修复 diff**：修复是局部的，复查就是局部；不要重新全量审。
6. **检查合并**：每个切片只跑相关测试；全量检查在最终审核前和最终提交前各一次。
