# 评审规则：只看最终交付物

两个仓库拿到同一个开放问题，但由各自的工作流自由发挥。评审不看流程名称、会话数或提交数；只看最终仓库里的东西。

每个维度 1–5 分，1 = 明显缺失/不可用，3 = 能用但有明显缺口，5 = 完整、好用、有证据。总分 30。

| 维度 | 看什么 |
|---|---|
| 产品用途 | 能不能支持每周复盘：查看、过滤、排序、合计、导出；是否形成一致的使用方式 |
| 正确性 | 核心输出正确；空结果、边界值、非法参数有处理；原有 `export` 仍工作 |
| 测试 | 测试能跑、覆盖关键行为、覆盖边界；不是只测 happy path |
| 设计与文档 | 现行设计/行为说明清楚；读者能从文档学会用；假设有记录；没有过时说明 |
| 代码质量 | 结构简单、标准库、没有明显过度设计；改动范围合理 |
| 收尾 | 仓库干净、无临时文件/未完成卡片；提交或工作树状态可解释 |

## 输出格式

对每个仓库输出：

```text
A:
  产品用途: n/5 — 证据
  正确性: n/5 — 证据
  测试: n/5 — 证据
  设计与文档: n/5 — 证据
  代码质量: n/5 — 证据
  收尾: n/5 — 证据
  总分: n/30

B:
  ...
```

最后用一句话说明哪边更适合这个开放任务，以及最大的不确定性。不要修改任何文件。
