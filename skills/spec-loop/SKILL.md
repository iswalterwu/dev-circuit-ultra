# spec-loop

目标：快，而且不丢质量。用户只在两处出场：**点头**（意图卡）和**验收**（每个切片），其余由你推进。

三条原则：一件事只放一个地方；审代码，不审文档；一刀一审。

## 1. 开工

1. 读项目 `AGENTS.md`，按它的路由表只读当前任务需要的文件。
2. 按下表判断走哪条路线，用一行告诉用户；用户可以推翻。
3. 接手进行中的功能：读 `specs/<feature>/spec.md` 的"切片"一节，再看 `git log`，从第一个没勾的步骤继续。

| 路线 | 适用 | 走哪几步 |
|---|---|---|
| 功能 | 新的用户可见行为 | ① → ⑤ |
| 快车道 | 修 bug、小改、不改行为的重构、文档、依赖、配置 | ③；命中风险加项时加 ④；最后写提交说明 |
| 探索 | 想先看效果（尤其是界面），或验证技术可行性 | 做一次性原型，不进产品代码，不写测试；把收获带回 ①，原型删掉 |

**风险加项**：数据迁移或删除、安全/隐私/凭证、真实资金或真实外部调用、不可逆操作、跨功能的契约变化。它可以叠加在任何路线上，命中时：

- 执行危险步骤前单独问用户；
- 审核时把它列为重点；
- PR 里写清怎么回滚。

**不加审核轮次。**

## 2. 五步循环

### ① 意图卡

- 按 `templates/spec.md` 写 `specs/<feature>/spec.md`，通常 1–2 页。
- 界面类功能：先做可点原型（放在仓库外，或放在被 Git 忽略的位置）。用户看过、给了反馈，再写卡。
- "待定"一节里的每一条，都写上你建议的默认值。只问会改变范围或验收的问题，而且一次问完。
- 请用户点头时用这个格式：

  ```
  请点头：specs/<feature>/spec.md
  要做：…    不做：…
  验收例子：A1–An（共 n 条）
  待定（已填默认）：…
  第一刀：…
  ```

- 点头之后，卡片仍然是活文档：澄清细节可以直接改；增删验收例子、改范围，必须先问用户。

### ② 只拆下一刀

- 选下一个最小的端到端增量，要求一个会话能做完。
- 在卡片的"切片"一节写 3–8 个步骤：改哪里、加哪些测试。后面的切片只留一行标题。
- 不建单独的计划文件，也不提前把所有任务拆完。

### ③ 实现 + 验证（和 ② 在同一个会话里完成）

- 测试分档：
  - 核心逻辑、契约、状态机、迁移、安全：先写测试；
  - 界面基元：做冒烟和无障碍断言；
  - 关键路径：最多 1 条端到端测试；
  - 纯样式：靠截图或人工看。
- 开发中跑相关测试；切片结束时，跑项目 AGENTS.md 列出的全部提交前检查。
- 做完的步骤就勾掉。持久规则有变化时更新 docs，只写现在。
- 提交说明格式见第 4 节。

### ④ 独立审一次

- 新开一个会话；尽量换一个模型家族，做不到就用同一模型的新会话。审核会话读同目录的 `reviewer.md`。
- 交给审核会话的话：`用 spec-loop 审核模式审 specs/<feature>/spec.md 的切片 Sx，基线 <base>。`
- 收到"必须改"：先修好，再把修复说明交回审核会话（或新开会话，并附上那份"必须改"清单），只复查这几条，最多复查一次。复查后仍有分歧，给用户两个选项，由用户选。
- 收到"建议"：顺手能做的当场做；其余要么丢掉，要么一行写进 `specs/backlog.md`。

### ⑤ 验收 + 合并

- 给用户的验收说明用这个格式：

  ```
  切片 Sx 完成，请验收：
  改了什么：…
  怎么看：<命令 / 页面 / 操作步骤>
  审核：通过（必须改 n 条已修）
  风险：…
  ```

- 界面切片每一刀都要验收。非界面功能可以在意图卡的"风险"一节约定"功能结束时一起验收"。
- 用户确认后合并（分支约定见项目 AGENTS.md）。
- 整个功能做完后：
  - 持久规则并入 docs；
  - 剩下的事项一行一条写进 `specs/backlog.md`；
  - 删除 `specs/<feature>/`，提交说明写 `close <feature>`。

## 3. 谁决定什么

| 你直接决定，不问 | 必须问用户（尽量攒到点头或验收时一起问） |
|---|---|
| 实现细节、步骤顺序、切片内的重构、测试设计、文档措辞；不改变用户可见行为的小偏差（在验收说明里提一句） | 增删验收例子、改范围、风险加项里的动作、新增付费服务或外部依赖、改其他功能的契约 |

## 4. 一件事只放一个地方

| 内容 | 位置 |
|---|---|
| 要做什么、验收例子、进度 | `specs/<feature>/spec.md` |
| 做没做对 | 测试和 CI；界面类再加演示步骤 |
| 为什么这么做、历史 | 提交说明、PR 描述 |
| 产品的长期规则 | `docs/`，只写现在 |
| 零散的待做事项 | `specs/backlog.md`，一行一条，做完就删 |

不要建 plan、tasks、checklist、review、handoff、状态文件、ADR、维护记录或 history 目录。

提交说明 / PR 描述的格式：

```
<type>(<feature>): <切片标题>

为什么：…
做了什么：…
验证：<命令> 通过；覆盖 A1、A3
审核：<一行结论>
回滚：<命中风险加项时才写>
```

## 5. 完成标准（每个切片）

1. 本切片的每条验收例子，都有通过的测试，或者写明的演示步骤。
2. 项目 AGENTS.md 列出的提交前检查全部通过。
3. 意图卡已更新：步骤勾掉，切片标为完成；如果对后续切片有了新认识，就调整它们的标题。
4. 持久规则的变化已同步到 docs。
5. `python scripts/doc_guard.py` 通过。

## 6. 提速规则

1. 审代码，不审文档。
2. 一刀审一次，复查最多一次；不按任务审，也不按阶段审。
3. 只计划下一刀。
4. 一个切片一个会话，审核另开一个会话；不需要上下文阈值。
5. 默认在同一个会话里实现。只有互不相关的大范围检索或机械改动，才并行派子 agent；不要"每个任务派一个子 agent 再审一次"。
6. 开发中跑相关测试，切片结束时跑一次全量。
7. 同时在研的功能最多 2 个，即 `specs/` 下的功能目录不超过 2 个。
8. 不重读整份文档，按路由只读需要的那一节。
9. 做功能时不改流程。觉得流程不顺，在回复里告诉用户。

## 7. 文档规则

- 只写现在。不写决策编号、日期、批准记录、模型和通道、哈希，也不写"原为 / 已取代 / 移植自"。理由写进提交说明。
- 长文档开头放一个"读我"块（模板见 `templates/doc-header.md`）：本文回答什么、不回答什么、任务到小节的路由、带锚点的目录。
- 会被别处引用的小节，加英文锚点 `<a id="...">`。
- 同一个事实只写在一处，其他地方放链接。
- 不翻 Git 历史找规则，除非用户要求。

## 8. 与其他技能的关系

- 本流程是功能开发的唯一流程。superpowers 只当技巧用：test-driven-development、systematic-debugging、verification-before-completion、receiving-code-review。
- 不生成 `docs/superpowers/` 下的文件；不用 writing-plans 写计划文件；不用 subagent-driven-development。brainstorming 的提问方式可以用来写意图卡，但产物只写进意图卡。
- 不用 OpenSpec 新开变更。如果项目里还有进行中的 OpenSpec 变更，先按 OpenSpec 把它收尾。

## 9. 接入新项目

1. 把 `templates/AGENTS.md` 复制到项目根目录，填上项目事实：命令、代码地图、红线。
2. 项目根目录的 `CLAUDE.md` 只写一行：`@AGENTS.md`。
3. 建 `specs/` 目录，把 `templates/backlog.md` 放进去，改名为 `specs/backlog.md`。
4. 设置防回流检查：
   - 把 `scripts/doc_guard.py` 复制到项目的 `scripts/`；
   - 新建 `.githooks/pre-commit`，在里面运行它；
   - 执行 `git config core.hooksPath .githooks`；
   - CI 里加一步 `python scripts/doc_guard.py`。
5. 长文档按 `templates/doc-header.md` 加上"读我"块。
