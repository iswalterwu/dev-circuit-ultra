# dev-circuit-ultra：框架设计

只在识别时衔接四问有一问答"不行"、或新项目的第一个功能时读；普通功能用不到本文件。

## 澄清

1. 说清缺口：现有框架为什么接不住，对应衔接四问的哪一问。
2. 给 2–3 个结构方案（模块与依赖方向、数据归属、契约与边界），写清取舍，推荐一个。方案只在对话里出现。
3. 构建者检查：假设要按推荐方案动手、却联系不上作者，列出猜错会造成实质影响的问题。文档里已有答案的不问；小问题自己定，列出你替用户定了什么。
4. 一轮最多 3 个只影响结构或边界的问题，和方案一起发出，然后结束本轮回复。什么样的回复算定了，按 SKILL.md ③的停止点；定了之前不写文件、不改代码。用户想要时，可以加一次结构审（`reviewer.md` 的结构审模式）。

## 定了以后

1. 建分支 `feat/<feature>`，改 `docs/architecture.md`（没有就新建）：
   - 开头是框架摘要，用 `<a id="summary"></a>` 标出，不超过 60 行：模块与依赖方向、数据归属、契约与扩展点、不可违背的约束。识别阶段只读这一段。
   - 正文写细节和关键决定，各附一句现行理由。
   - 迁移步骤写成卡的切片步骤；风险和待定问题在澄清时说清，不落盘。
2. 提交，再 `devcircuit ledger add --feature <feature> --kind framework --decision "<选定的结构>" --rejected "<被否方案>：<原因>"`。
3. 回到 SKILL.md 的 ③ 做功能设计。

## 第一个切片：骨架切片

打通一条贯穿所有模块、覆盖风险最高路径的最细端到端路径。内部可以用桩，但模块之间的连线和契约测试必须是真的；能写成测试的依赖规则在这个切片里写成测试。
