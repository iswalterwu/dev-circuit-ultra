# dev-circuit-ultra

目标：更少上下文、更少流程、更快交付，不丢质量。三条原则：设计是唯一现行源，变更时原地覆盖或删除旧内容；一件事只放一个地方；流程按需加，不默认加。

用户只在三处参与：设计澄清时回答问题、选方案；点头确认要求改动和意图卡；验收。其余由你推进。

## 0. 边界：历史在项目外

- 只读项目里的现行设计（能力规格、docs、架构）、代码和测试。不读、不搜项目外的账本，也不运行 `dev-circuit-archivist`；需要历史时停下来问用户，由用户决定要不要用 `dev-circuit-ledger` 给你一份最小 brief。
- 项目里只写现在：不写决策编号、日期、批准记录、模型和通道、哈希，不写"原为 / 已取代 / 移植自 / 放弃的备选"。被否方案和废弃思路由项目外的 archivist 记录。

## 1. 开工

1. 读项目 `AGENTS.md`，按它的路由只读当前任务需要的设计、代码和受影响的能力规格。项目里已经回答了的，不再问用户。
2. 选路线，用一行告诉用户；用户可以推翻。
3. 接手进行中的功能：读 `specs/<feature>/spec.md` 的切片和 `git log`，从第一个没勾的步骤继续。
4. 新建项目、给项目接入本流程或建账本：读本技能目录的 `setup.md`。

| 路线 | 适用 | 做什么 |
|---|---|---|
| 功能 | 新的用户可见行为，或框架级改动（用户看不到变化也算） | 第 2 节 ① → ④ |
| 快车道 | 修 bug、小改、不改行为的重构、文档、依赖升级、配置（框架级的除外） | 只做 ③，写提交说明 |
| 探索 | 先看效果（尤其是界面）、验证技术可行性 | 一次性原型，不进产品代码，不写测试；收获带回 ①，原型删掉 |

**框架级**（命中任一条）：新建模块、包或服务，或引入新的架构模式；核心数据模型或持久化结构变化；组件之间新增或改动契约（API、进程间通信、MCP、文件格式）；新增外部依赖；贯穿全局的机制（错误模型、状态、并发、权限）；复杂的安全、性能或迁移；动手前就该定下来的重大歧义；新项目的第一个功能。拿不准就按普通处理；新增一个命令、参数、输出格式或测试，本身不算框架级。框架级另读 `framework.md`。

**风险加项**（任何路线都可能命中）：数据迁移或删除、安全 / 隐私 / 凭证、真实资金或真实外部调用、不可逆操作、跨功能的契约变化。执行危险步骤前单独问用户，并提一句可以加一次独立审核，由用户定；提交说明写清怎么回滚。

## 2. 功能循环

### ① 设计澄清 + 点头

- 先读现行设计；这次功能是设计 delta，不是重写产品。
- 问会改变行为、契约、边界、范围或验收的问题，一次一个；设计级歧义必须问，不靠默认值；低影响的问题自己定。普通功能把问题攒到点头时一次问完。
- 新页面或交互有歧义的界面，先做可点原型，用户看过再定；交互清楚的小改用一句话描述。
- 行为要求直接改在 `docs/requirements/<能力>.md`（新能力先按 `templates/requirements.md` 建文件）：新增的写编号和例子，修改的原地改写，删除的直接删掉。这就是本功能的验收例子，别处不再写一份。
- 按 `templates/spec.md` 写 `specs/<feature>/spec.md`，只写目标、范围、切片。
- 请用户点头时列出：卡的路径；要做 / 不做；要求改动（新增 / 改写 / 删除哪些编号）；普通还是框架级；第一个切片。
- 点头后的改动谁来定见第 3 节；任何改动都原地覆盖，只留现行版本。

### ② 规划一个切片

选下一个能独立验收、一个会话做得完的端到端切片；在卡的"切片"一节写 3–8 个步骤（改哪里、加哪些测试），后面的切片只留一行标题。实现和测试范围从现行设计推导；不建计划文件或测试矩阵，不提前拆所有任务。

### ③ 实现 + 验证（和 ② 在同一个会话里）

- 测试分档：核心逻辑、契约、状态机、迁移、安全先写测试；界面基元做冒烟和无障碍断言；关键路径最多 1 条端到端测试；纯样式截图或人工看。
- 测试文件里写上它证明的要求编号（如注释里的 `DOCK-12`），这就是证明，能力规格里不写测试路径；`spec_check --report` 靠它列出没有测试的要求。
- 开发中只跑相关测试。功能在请用户验收前、快车道在提交前，跑一次 AGENTS.md 列出的全部提交前检查（含 `doc_guard`、`spec_check`）；修复后提交前再跑一次。
- 默认在本会话里实现；只有互不相关的大范围检索或机械改动才并行派子 agent。
- 设计变了，先改能力规格或设计（覆盖 / 删除），再改代码和测试。用户可见的交互语义或界面规则变了，同一个切片里同步对应的 docs。
- 勾掉做完的步骤，切片做完标 ✓。

### ④ 验收 + 收尾

- 请用户验收前确认：本切片涉及的每条要求都有通过的测试或写明的演示步骤；能力规格和 docs 与实现一致；③ 里的全量检查已通过。
- 验收说明写三行：改了什么、怎么看（命令 / 页面 / 步骤）、风险。界面切片逐个验收；非界面功能在功能结束时一起验收。
- 能力规格和 `docs/architecture.md` 从点头起就是现行的，收尾不用合并。
- 用户确认后合并，分支约定见 AGENTS.md。功能做完后，剩下的事项一行一条写进 `specs/backlog.md`，删除 `specs/<feature>/`，提交说明写 `close <feature>`。

### 按需：独立审核

只在用户要求时做（"审一下这个切片""审一下这个设计"），包括用户接受了风险加项或框架级点头时提的审核。

- 派一个独立上下文的只读子 agent，用户点名了 agent 就用它；宿主不支持子 agent 时，请用户新开会话审。不在同一个上下文里自审，也不让实现 worker 冒充 reviewer。
- 只交给它：`reviewer.md`、`specs/<feature>/spec.md`、基线 `<base>`、`git diff <base>...HEAD`。
- "必须改"修好后，只把修复 diff 交回同一个 reviewer 复查，最多一次；仍有分歧，给用户两个选项。"建议"顺手能做的当场做，其余丢掉或一行写进 `specs/backlog.md`。

## 3. 谁决定什么

- 你定：实现细节、步骤顺序、切片内的重构、测试设计、文档措辞，以及不改变用户可见行为的小偏差（验收时提一句）。
- 问用户（尽量攒到点头或验收时）：增删要求、改范围、改设计边界 / 契约 / 关键决定、改结构、风险加项里的动作、新增付费服务或外部依赖、改其他功能的契约。

## 4. 一件事只放一个地方

| 内容 | 位置 |
|---|---|
| 目标、范围、切片进度 | `specs/<feature>/spec.md`，功能做完就删 |
| 现行的、可验证的行为要求 | `docs/requirements/<能力>.md`（能力规格），在研功能也直接改这里 |
| 现行的结构与关键决定 | `docs/architecture.md`，在研的框架级功能也直接改这里 |
| 产品语义、交互与设计说明 | `docs/` 下其他文档，引用要求编号，不重复写要求 |
| 做没做对 | 测试和 CI；界面类再加演示步骤 |
| 为什么、历史、被否方案 | 项目外的私有账本 |
| 零散的待做事项 | `specs/backlog.md`，一行一条，做完就删 |

- 编号：每份能力规格的文件头声明一个代号（2–8 个大写字母）；要求编号写成 `<代号>-<数字>`，全局唯一，只增不复用。老项目的 `AC-xxx-y` 原样保留，在代码和测试里写成 `<代号>:AC-xxx-y`。
- 不建 plan、tasks、checklist、review、handoff、状态文件、ADR、维护记录、history 或 ledger 目录；同时在研的功能最多 2 个。
- 提交说明：`<type>(<feature>): <切片标题>`，正文写为什么、做了什么、涉及的要求编号、验证命令；命中风险加项时加回滚方式。

## 5. 文档

- 只写现在（见第 0 节）。唯一的例外：`docs/architecture.md` 里的关键结构决定可以附一句现行理由，防止后来者把结构改回去。
- 长文档开头放"读我"块（`templates/doc-header.md`）；会被别处引用的小节加英文锚点 `<a id="...">`。
- 按路由只读需要的那一节，不重读整份文档；除非用户要求，不翻 Git 历史找规则。

## 6. 与其他技能

- 在使用本技能的项目里，这是唯一的功能开发流程：不调用 brainstorming、writing-plans、subagent-driven-development，不生成 `docs/superpowers/` 下的文件；不用 OpenSpec 新开变更，还有进行中的 OpenSpec 变更时先按 OpenSpec 收尾。
- 技巧类技能照常使用：test-driven-development、systematic-debugging、verification-before-completion、receiving-code-review。
- 做功能时不改流程；觉得不顺，在回复里告诉用户。
