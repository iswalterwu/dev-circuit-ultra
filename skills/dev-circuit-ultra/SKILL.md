# dev-circuit-ultra

目标：快，而且不丢质量。设计是唯一现行源；开发 agent 只读现行设计，不读账本。

用户在关键节点参与：
- **设计澄清与选方案**：写卡前回答设计问题、选择方案；设计级歧义不靠默认值。
- **点头**：确认现行设计和意图卡；框架级改动连同结构设计一起确认。
- **验收**：界面切片逐个确认；非界面功能可在卡里约定功能结束时一起验收。

其余由你推进。

四条原则：设计是源；一件事只放一个地方；审代码对现行设计；逐切片审核。

## 0. 两条边界

- **开发侧**：只读项目里的现行设计、能力规格、代码和测试。不要读项目外的账本，不要建决策记录/历史目录，不要把废弃方案写进任何项目文档。
- **记账侧**：由独立 `dev-circuit-archivist` 在单独会话/容器里运行；项目只读、账本只写；不改代码/设计，不把账本内容返回给开发 agent。账本是项目外的私有 git repo，只供 human 回溯。
- **human**：唯一能同时看两边的人；需要历史时，由 human 让 `dev-circuit-ledger` 生成最小 brief，再决定是否交给开发 agent。

开发 agent 不运行 archivist，也不读账本。需要历史时停下来问用户。

## 1. 开工

1. 读项目 `AGENTS.md`，按它的路由表读取现行设计/架构、相关代码与文档，以及受影响的能力规格。**先读再问**：项目和文档已经回答了的，不要再问用户。不要搜索项目外的账本或历史目录。
2. 按下表判断走哪条路线，用一行告诉用户；用户可以推翻。
3. 接手进行中的功能：读 `specs/<feature>/spec.md` 的"切片"一节（框架级再读同目录的 `design.md`）和 `git log`，从第一个没勾的步骤继续。

| 路线 | 适用 | 走哪几步 |
|---|---|---|
| 功能 | 新的用户可见行为，或命中第 2 节任一条的改动（用户看不到变化也算） | ① → ⑤ |
| 快车道 | 修 bug、小改、不改行为的重构、文档、依赖升级、配置（命中第 2 节任一条的除外） | ③；命中风险加项时加 ④；最后写提交说明 |
| 探索 | 想先看效果（尤其是界面）、验证技术可行性 | 做一次性原型，不进产品代码，不写测试；把收获带回 ①，原型删掉 |

**风险加项**：数据迁移或删除、安全 / 隐私 / 凭证、真实资金或真实外部调用、不可逆操作、跨功能的契约变化。它可以叠加在任何路线上，命中时：

- 执行危险步骤前单独问用户；
- 审核时把它列为重点；
- PR 里写清怎么回滚。

**不加审核轮次。**

## 2. 普通还是框架级

每张意图卡的"结构影响"一节要回答两件事：动哪些模块；有没有新契约、新数据结构或全局机制。命中下面任意一条，就是**框架级**：

- 新建模块、包或服务；引入新的架构模式；
- 核心数据模型或持久化结构变化；
- 组件之间新增或改动契约（API、进程间通信、MCP、文件格式）；
- 新增外部依赖；
- 贯穿全局的机制：错误模型、状态、并发、权限；
- 安全、性能或迁移比较复杂；
- 动手前就该定下来的重大歧义；
- 新项目的第一个功能。

拿不准时，按框架级处理。

## 3. 五步循环

### ① 设计澄清 + 意图卡（现行设计）

**所有功能都要做的：**

- 先读产品现行设计和架构。这次功能是设计 delta，不是重写产品。
- **clarify 设计**：问会改变设计、行为、契约、边界、范围或验收的问题；一次一个问题；设计级歧义必须问，不能靠默认值。
- 按 `templates/spec.md` 写 `specs/<feature>/spec.md`，通常 1–2 页；`## 设计` 写现行行为、边界和契约；框架级再按 `templates/design.md` 写 `design.md`。
- "规格变化"一节就是本功能的验收例子：用能力规格的编号写新增、修改、删除哪些要求（编号规则见第 5 节）。
- "待定"只放低影响问题；设计级问题在点头前问掉，不能填默认值混过去。
- 新页面或交互有歧义的界面，先做可点原型，用户看过、给了反馈，再写卡；加按钮这类交互清楚的小改，用一句话描述即可。

**普通功能**：设计写 3–8 行就够；只问会改变设计、范围或验收的问题，攒到点头时一次问完。

**框架级，按以下顺序做：**

1. **问意图和设计约束**：一次一个问题，问会改变结构或边界的问题，通常不超过 3 轮。
2. **给方案**：2–3 个结构/行为方案，写清各自取舍，推荐一个，让用户选。方案只在对话里出现；用户选定后，设计里只写选中的方案，被否方案不落盘。
3. **写卡和设计**：用户选定方案后，写意图卡，再按 `templates/design.md` 写 `specs/<feature>/design.md`。设计只写现行结构、边界、契约和现行理由。
4. **构建者检查 + 结构审**：由实现会话派一个结构审核子 agent（独立上下文，优先换模型家族），按 `reviewer.md` 的"结构审模式"做，复查最多一次；宿主不支持子 agent 时才新开会话。构建者提出的问题分三类处理：
   - 文档里已有答案的，补进文档；
   - 小问题，自己定，在文档里标"我的判断"；
   - 只能用户定的，点头时一起问。
5. **把第一个切片定为骨架切片**：打通一条贯穿所有模块、覆盖风险最高路径的最细端到端路径。内部可以用桩，但模块之间的连线和契约测试必须是真的。

**请用户点头时用这个格式：**

```
请点头：specs/<feature>/spec.md（框架级另附 design.md）
要做：…    不做：…    反目标：…
设计：<一句话现行设计；边界/契约>
规格变化：新增 n 条 / 修改 n 条 / 删除 n 条
结构：普通 / 框架级 —— <一句话结构摘要>
待定（只列低影响项）：…
第一个切片：…
```

点头之后，卡片和设计仍然是活文档，但只保留现行版本：
- 澄清细节，可以直接改；
- 增删要求、改范围、改设计边界/契约/关键决定，要先问用户；
- 设计变更原地覆盖或删除旧内容；不写"原为 / 已取代 / 放弃的备选"；被否方案由外置账本记录，不写进项目。

### ② 只规划一个切片

- 选下一个能独立验收的端到端切片，一个会话能做完；框架级的第一个切片是骨架切片。
- 在卡片的"切片"一节写 3–8 个步骤（改哪里、加哪些测试）；后面的切片只留一行标题。
- 实现和测试范围从现行设计推导；不建 test matrix、不建单独的计划文件，不提前拆所有任务。

### ③ 实现 + 验证（和 ② 在同一个会话里）

- **测试分档**：
  - 核心逻辑、契约、状态机、迁移、安全：先写测试；
  - 界面基元：冒烟和无障碍断言；
  - 关键路径：最多 1 条端到端测试；
  - 纯样式：截图或人工看。
- 测试名里带上它证明的要求编号，例如 `DOCK-12`。
- 开发中跑相关测试；切片结束时，跑项目 AGENTS.md 列出的全部提交前检查。
- 设计变了：先改设计（覆盖/删除），再改代码/测试；不要留着旧设计让实现漂移。
- 勾掉做完的步骤。用户可见的交互语义或界面规则变了，就在同一个切片里同步对应的 docs。

### ④ 独立审核一次

- 由实现会话自动派一个审核子 agent，不需要用户另开会话。用宿主提供的子 agent 工具（例如 Claude Code 的 Task、pi 的 subagent）；子 agent 使用独立上下文，不继承实现过程的对话。
- 优先给子 agent 换一个模型家族；做不到就用同模型的独立上下文，不要退回同一个上下文自审。
- 交给子 agent 的只有：`reviewer.md`、`specs/<feature>/spec.md` 的当前切片和现行设计、基线 `<base>`、`git diff <base>...HEAD`。不要附上实现者的解释、账本或历史。
- 收到"必须改"：修好后，把修复说明和新的 diff 交回同一个审核子 agent 复查；复查最多一次。仍有分歧，给用户两个选项，由用户选。
- 收到"建议"：顺手能做的当场做；其余丢掉，或者一行写进 `specs/backlog.md`。
- 宿主确实不支持子 agent 时，才让用户开一个审核会话；这是降级方案，不是默认流程。

### ⑤ 验收 + 合并

- **收尾放在最后一个切片里做**，这样它会被那个切片的审核看到。最后一个切片的步骤要包括：
  - 把"规格变化"合并进 `docs/requirements/<能力>.md`；
  - 合并后，把卡里这一节的标题改成 `## 规格变化（已合并）`；spec_check 只检查标题恰好是 `## 规格变化` 的节；
  - 框架级：把 `design.md` 里仍然有效的结构、边界和关键决定，并入 `docs/architecture.md`（每个关键决定可以附一句现行理由）。
  - 由 human/orchestrator 在项目外让 archivist 记录被删除/被替代的设计决策；开发 agent 不写账本，也不读账本。
- 给用户的验收说明：

  ```
  切片 Sx 完成，请验收：
  改了什么：…
  怎么看：<命令 / 页面 / 步骤>
  审核：通过（必须改 n 条已修）
  风险：…
  ```

- 界面切片逐个验收；非界面功能可以在意图卡的"风险"一节约定"功能结束时一起验收"。
- 用户确认后合并，分支约定见项目 AGENTS.md。
- 整个功能做完后：剩下的事项一行一条写进 `specs/backlog.md`；删除 `specs/<feature>/`，提交说明写 `close <feature>`。

## 4. 谁决定什么

| 你直接决定，不问 | 必须问用户（尽量攒到点头或验收时一起问） |
|---|---|
| 实现细节、步骤顺序、切片内的重构、测试设计、文档措辞；不改变用户可见行为的小偏差（在验收说明里提一句） | 增删要求、改范围、改设计边界/契约/关键决定、改结构、风险加项里的动作、新增付费服务或外部依赖、改其他功能的契约 |

## 5. 一件事只放一个地方

| 内容 | 位置 |
|---|---|
| 要做什么、本功能的要求变化、进度 | `specs/<feature>/spec.md` |
| 框架级的结构与关键决定（在研期间） | `specs/<feature>/design.md` |
| 现行的、可验证的行为要求 | `docs/requirements/<能力>.md`（能力规格） |
| 现行的结构与关键决定 | `docs/architecture.md` |
| 产品的语义、交互与设计说明 | `docs/` 下其他文档，引用要求编号，不重复写要求 |
| 做没做对 | 测试和 CI；界面类再加演示步骤 |
| 为什么这么做、历史、被否方案 | 项目外的私有账本；只有 human 能读，开发 agent 不读 |
| 零散的待做事项 | `specs/backlog.md`，一行一条，做完就删 |

**编号规则：**
- 每份能力规格的文件头声明一个代号，由 2–8 个大写字母组成；要求的编号写成 `<代号>-<数字>`，全局唯一，只增不复用。
- 老项目已有的 `AC-xxx-y` 编号原样保留，只要求在所属能力规格内唯一。在意图卡里引用时写成 `<代号>:AC-xxx-y`。
- 新能力在写卡时就建好能力规格文件（可以只有文件头）；要求本身在最后一个切片合并进去。在研卡里新增的编号，spec_check 视为已存在，测试从第一个切片起就能引用。

不要建 plan、tasks、checklist、review、handoff、状态文件、ADR、维护记录、history 目录或账本目录。

**提交说明 / PR 描述的格式：**

```
<type>(<feature>): <切片标题>

为什么：…
做了什么：…
规格：DOCK-12、DOCK-31
验证：<命令> 通过
审核：<一行结论>
回滚：<命中风险加项时才写>
```

## 6. 完成标准（每个切片）

1. 本切片涉及的每条要求，都有通过的测试，或者写明的演示步骤；测试和实现与现行设计一致。
2. 项目 AGENTS.md 列出的提交前检查全部通过，包括 `python scripts/doc_guard.py` 和 `python scripts/spec_check.py`。
3. 意图卡已更新：步骤勾掉，切片标为完成；如果对后续切片有了新认识，就调整它们的标题。
4. 交互语义或界面规则的变化，已同步到 docs；如果是最后一个切片，规格变化和结构决定也已合并。

## 7. 提速规则

1. 审代码对现行设计，不审文档措辞。框架级的结构审是例外，它在写代码前只做一次。
2. 每个切片审核一次，复查最多一次；不按任务审，也不按阶段审。
3. 只计划下一个切片。普通功能不写单独的 `design.md`，但卡里必须有现行设计一节。
4. 一个切片一个会话；审核由实现会话派独立子 agent 完成，不另开用户会话。
5. 默认在同一个会话里实现。只有互不相关的大范围检索或机械改动才并行派子 agent；审核子 agent 是例外，它只在切片结束时派一次，不按任务重复派。
6. 开发中跑相关测试，切片结束时跑一次全量。
7. 同时在研的功能最多 2 个，即 `specs/` 下的功能目录不超过 2 个。
8. 不重读整份文档，按路由只读需要的那一节。
9. 做功能时不改流程。觉得流程不顺，在回复里告诉用户。
10. 不读、不写账本；archivist 在项目外异步运行，不进入开发上下文。

## 8. 文档规则

- 只写现在：不写决策编号、日期、批准记录、模型和通道、哈希，也不写"原为 / 已取代 / 移植自 / 放弃的备选"。设计变更原地覆盖或删除旧内容；被否方案/废弃思路由项目外账本记录，不写进项目。唯一的例外是：`docs/architecture.md` 里每个关键结构决定，可以附一句现行理由，用来防止后来者把结构改回去。
- 可验证的行为要求只写在能力规格里；其他文档引用编号，不重复写要求。
- 长文档开头放"读我"块（`templates/doc-header.md`）：本文回答什么、不回答什么、任务到小节的路由、带锚点的目录。
- 会被别处引用的小节，加英文锚点 `<a id="...">`。
- 不翻 Git 历史找规则，除非用户要求。

## 9. 与其他技能的关系

- 本流程是功能开发的唯一流程。它已经包含设计澄清、方案比较和构建者检查，所以在使用 dev-circuit-ultra 的项目里，不调用 brainstorming、writing-plans、subagent-driven-development，也不生成 `docs/superpowers/` 下的文件。
- 记账不是本流程的一步：`dev-circuit-archivist` 在项目外的独立会话/容器运行；`dev-circuit-ledger` 只供 human 查询。开发 agent 不读账本，也不能把账本内容带进上下文。
- superpowers 的技巧类技能照常使用：test-driven-development、systematic-debugging、verification-before-completion、receiving-code-review。
- 不用 OpenSpec 新开变更；项目里还有进行中的 OpenSpec 变更时，先按 OpenSpec 收尾。

## 10. 新建项目、接入 dev-circuit-ultra 与账本

项目初始化和账本初始化是两件事，账本永远在项目外。

最快的方式是运行本技能目录里的脚本：

- **新建**：`pwsh -NoProfile -File <本技能目录>/scripts/new-project.ps1 -Path <项目目录> -Name <项目名>`。它会生成下面第 1–5 步的全部文件，执行 `git init`，并做第一次提交。
- **接入已有仓库**：同一命令加 `-Adopt`。它只补缺失的文件，已有文件不覆盖，也不提交，最后会报出 doc_guard 发现的旧文档问题。
- **账本**：用 `scripts/new-ledger.ps1 -Path <项目外的私有目录>` 创建独立私有 git repo；不要把账本放进项目，也不要让开发容器挂载它。

跑完脚本后，仍要填写 AGENTS.md 里的项目事实。不用脚本时，按下面的步骤手动做：

1. 把 `templates/AGENTS.md` 复制到项目根目录，填上项目事实：命令、代码地图、红线。
2. 项目根目录的 `CLAUDE.md` 只写一行：`@AGENTS.md`。
3. 建 `specs/` 目录，把 `templates/backlog.md` 放进去，改名为 `specs/backlog.md`。
4. 建 `docs/requirements/`，放入 `templates/project/docs/requirements/README.md`；以后每个能力一份规格，按 `templates/requirements.md` 写。
5. 设置检查：
   - 把 `scripts/doc_guard.py` 和 `scripts/spec_check.py` 复制到项目的 `scripts/`；
   - 新建 `.githooks/pre-commit` 依次运行这两个脚本，然后执行 `git config core.hooksPath .githooks`；
   - CI 里也加上这两步。
6. 长文档按 `templates/doc-header.md` 加上"读我"块。
