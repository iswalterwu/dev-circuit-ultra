# dev-circuit-ultra

目标：一次交付一个功能，成本低于 OpenSpec，读得少但不漏读。三条原则：设计是唯一现行源，变更时原地覆盖或删除旧内容；一件事只放一个地方；机械能做的交给 `devcircuit` 命令，不靠自觉。

用户只在三处参与：框架澄清（需要时）、功能澄清、验收。其余由你推进。

## 0. 边界

- 只读项目里的现行设计、代码和测试。账本在项目外，对你只写不读：用 `devcircuit ledger add` 写，用 `devcircuit ledger check` 核对，不用别的办法碰它。需要历史时问用户。
- 项目里只写现在：不写决策编号、日期、批准记录、模型和通道、哈希，不写"原为 / 已取代 / 放弃的备选"。为什么、被否方案写进账本。

## 1. 识别：每个需求的第一步

1. 读项目 `AGENTS.md`，跑 `devcircuit context --map`：能力清单、在研功能、框架摘要在哪。项目里已经回答了的，不再问用户。
2. 归类，用一行告诉用户类别和理由；用户可以推翻。

| 类别 | 判断 | 下一步 |
|---|---|---|
| 在研功能的续做或修正 | 落在 `specs/<feature>/` 某张卡的范围里 | ④；范围变了先回 ③ |
| 已有能力的变化 | 改某份能力规格里的行为 | 过衔接四问 |
| 新能力 | 没有能力规格覆盖 | 过衔接四问 |
| bug | 行为不符合现行要求 | 快车道：修 + 测试（引用被违反的编号），按 ⑤ 的条件审，写提交说明 |
| 探索 | 先看效果（尤其界面）、验证可行性 | 一次性原型，不进产品代码；收获带回 ③，原型删掉 |

**衔接四问**（读 `docs/architecture.md` 开头的框架摘要再答）：① 数据归哪个现有模块？② 只用现有扩展点和契约够不够？③ 要不要新的外部依赖、进程或持久化结构？④ 会不会违背框架摘要里的约束？有一问答"不行"进 ②；都"行"进 ③。新项目的第一个功能进 ②。拿不准就问用户。

**风险加项**（任何类别都可能命中）：数据迁移或删除、安全 / 隐私 / 凭证、真实资金或真实外部调用、不可逆操作、跨功能的契约变化。执行危险步骤前单独问用户；提交说明写清怎么回滚。

## 2. 框架设计（按需）

读本技能目录的 `framework.md`，按它澄清到用户说"定了"，把结构写进 `docs/architecture.md`，再进 ③。

## 3. 功能设计

- 用 `devcircuit context --capability <代号>` 或 `--ids <编号>` 读受影响的现行要求；这次是设计 delta，不是重写产品。交互有歧义的新页面，先做可点原型给用户看。
- 在对话里发设计摘要，不超过 25 行：要求变化（新增 / 改写 / 删除哪些编号，每条带例子；新的命令、接口或输入至少写一条出错时的要求，或写明"无失败路径"；兼容指以前能成功的输入照样成功、输出不变，把崩溃改成可读错误不算破坏兼容）；做 / 不做；怎么验收；第一个切片；你替用户定了哪些小事。
- 只问会改变行为、契约、范围或验收的问题，一轮最多 3 个，和摘要一起发；低影响的自己定。
- **停止点**：发出摘要就结束本轮回复。用户的回复里有提问、回答或补充，就不算定了，哪怕同时说了"其他按你的建议"：只发变化的部分，问一句"定了吗？"，再停。回复里没有新内容、只是同意（"定了""可以，开始做吧""没问题"）才算定了；定了之前不写文件、不改代码。
- "定了"之后：
  1. 建分支 `feat/<feature>`（框架设计时已建就沿用）；功能名只用字母、数字、点、下划线和连字符，一段，不含斜杠，卡目录、分支和账本都用它；
  2. 按 `templates/requirements.md` 改能力规格（新能力先建文件）：新增的写编号和例子，修改的原地改写，删除的直接删掉；
  3. 按 `templates/spec.md` 写卡，提交；
  4. `devcircuit ledger add --feature <feature> --kind design --decision "<选定的设计>" --rejected "<被否方案>：<原因>" --ids <涉及的编号>`，删掉的编号用 `--removed-ids`。

## 4. 实现：一次一个切片

- 每个会话开头跑 `devcircuit context --feature <feature>`：它给出卡、本功能改到或引用到的要求原文、相关测试路径，并列出省略了什么。按它补读，不整份读文档。
- 选下一个能独立验收、一个会话做得完的端到端切片，在卡的"切片"一节写 3–8 个步骤；后面的切片只留一行标题。不建计划文件或测试矩阵。
- 测试分档：核心逻辑、契约、状态机、迁移、安全先写测试；界面基元做冒烟和无障碍断言；关键路径最多 1 条端到端测试；纯样式截图或人工看。
- 测试文件里写上它证明的要求编号（如注释里的 `DOCK-12`），这就是证明，能力规格里不写测试路径；`spec_check --report` 靠它列出没有测试的要求。
- 开发中只跑相关测试。设计变了：先回 ③ 让用户定，再改能力规格或 `docs/architecture.md`，再改代码和测试，并 `ledger add --kind design-change`。
- 勾掉做完的步骤，切片做完标 ✓。一个分支只做这一个功能；冒出来的别的需求一行写进 `specs/backlog.md`。
- 默认在本会话里实现；只有互不相关的大范围检索或机械改动才并行派子 agent。

## 5. 审核 + 一轮修复

- 功能做完、请用户验收前审一次：派一个独立上下文的只读子 agent，模型按 AGENTS.md 的"审核模型"，没写就用当前模型；宿主不支持子 agent 时，请用户新开会话审。不自审，也不让实现 worker 冒充 reviewer。
- 只交给它：本技能目录里 `reviewer.md` 的完整路径、`devcircuit context --review <feature>` 的输出、基线 `<base>`、`git diff <base>...HEAD`。
- "必须改"修一轮，只把修复 diff 交回同一个 reviewer 复查一次；没修好的写进交付的"潜在问题"。"建议"顺手能做的当场做，其余一行写进 `specs/backlog.md`。
- 快车道只在改了契约（API、命令行、文件格式、数据结构）或 diff 超过约 200 行时审。框架设计时用户要求，可以加一次结构审（`reviewer.md` 的结构审模式）。

## 6. 验收、收尾、交付

- 请用户验收前确认：本功能涉及的每条要求都有通过的测试或写明的演示步骤；能力规格和 docs 与实现一致；AGENTS.md 列出的全部提交前检查已通过。界面切片逐个验收，其余在功能结束时一起验收。
- 用户确认后跑 `devcircuit close <feature> --summary "<一句话>" --review "<审核结果>"`：全量检查 → 账本核对 → 删卡并提交 `close <feature>` → 写收尾记录 → 再核对。核对报出的不一致，原因清楚的用 `ledger add --kind correction` 补记，不清楚的问用户。然后按 AGENTS.md 的分支约定合并。
- 最后的回复就是交付报告：

```
交付：<feature>（新能力 / 已有能力变化 / 在研修正 / bug）
做了什么：…（涉及的要求编号）
怎么验收：命令 / 页面 / 步骤
审核：必须改 N 条，已修 N 条；复查结论
潜在问题：没修好的必须改、没覆盖的要求、已知限制、账本核对结果
下一步建议：1–3 条（backlog、没做的建议、框架债务）
```

## 7. 谁决定什么

- 你定：实现细节、步骤顺序、切片内的重构、测试设计、文档措辞，以及不改变用户可见行为的小偏差（交付时提一句）。
- 问用户（尽量攒到澄清或验收时）：增删要求、改范围、改设计边界 / 契约 / 关键决定、改结构、风险加项里的动作、新增付费服务或外部依赖、改其他功能的契约。

## 8. 一件事只放一个地方

| 内容 | 位置 |
|---|---|
| 目标、范围、切片进度 | `specs/<feature>/spec.md`，收尾时删掉 |
| 现行的、可验证的行为要求 | `docs/requirements/<能力>.md`（能力规格） |
| 现行的结构与关键决定 | `docs/architecture.md`，开头是框架摘要 |
| 产品语义、交互与设计说明 | `docs/` 下其他文档，引用要求编号，不重复写要求 |
| 做没做对 | 测试和 CI；界面类再加演示步骤 |
| 为什么、被否方案、改过的决定 | 项目外的账本，`devcircuit ledger add` 写入 |
| 零散的待做事项 | `specs/backlog.md`，一行一条，做完就删 |

- 编号：每份能力规格的文件头声明一个代号（2–8 个大写字母）；要求编号写成 `<代号>-<数字>`，全局唯一，只增不复用。老项目的 `AC-xxx-y` 原样保留，在代码和测试里写成 `<代号>:AC-xxx-y`。
- 不建 plan、tasks、checklist、review、handoff、状态文件、ADR、维护记录、history 或 ledger 目录；不手写文档或能力的登记表，`devcircuit context --map` 现场生成。
- 提交说明：`<type>(<feature>): <切片标题>`，正文写为什么、做了什么、验证命令；命中风险加项时加回滚方式。

## 9. 文档

- 只写现在（见第 0 节）。唯一的例外：`docs/architecture.md` 里的关键结构决定可以附一句现行理由，防止后来者把结构改回去。
- 长文档开头放"读我"块（`templates/doc-header.md`）；会被别处引用的小节加英文锚点 `<a id="...">`。
- 体积上限：能力规格 400 行、框架摘要 60 行、卡 80 行，`doc_guard` 会报。超了就按子能力拆规格、精简摘要、把做完的切片收成一行。
- 除非用户要求，不翻 Git 历史找规则。

## 10. 与其他技能

- 在使用本技能的项目里，这是唯一的功能开发流程：不调用 brainstorming、writing-plans、subagent-driven-development，不生成 `docs/superpowers/` 下的文件；不用 OpenSpec 新开变更，还有进行中的 OpenSpec 变更时先按 OpenSpec 收尾。
- 技巧类技能照常使用：test-driven-development、systematic-debugging、verification-before-completion、receiving-code-review。
- 做功能时不改流程；觉得不顺，在回复里告诉用户。
- 新建项目、给项目接入本流程、建账本或升级旧项目：读本技能目录的 `setup.md`。
